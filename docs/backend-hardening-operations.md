# 后端与数据库加固：验收和上线说明

本轮保留 FastAPI、自有 JWT、PostgreSQL、CloudBase 和原生小程序架构。代码位于 `feat/daily-settlement` 工作区；本说明中的本地验证不代表生产环境已部署。

## 已实现的行为

| 范围 | 行为 | 兼容边界 |
| --- | --- | --- |
| 保存消费 | 校验成员、币种、金额精度、明细 ID、分摊比例、汇率、实际支付及大小上限 | 旧数据继续可读；编辑保存时必须满足校验，不能静默修复旧账 |
| 历史结清 | 创建者预览并确认未付、全付或部分已付；保存确认人、时间、选择及全部原消费快照 | 不从旧“发布结算”推断已付款；历史确认页面尚未接入 |
| 转账记录 | `trip_ledgers.state_json` 是唯一写入源；`payment_records`、`payment_allocations` 为同事务生成的可查询投影 | 不能改写已确认金额或删除审计记录；撤销保留原记录 |
| 查询 | 首页直连路径固定四次集合查询；CloudBase 路径一次批量 RPC；新增有上限的消费分页 | 原全量列表保留，旧页面不会因分页截断漏账；大账本汇总仍需读取明细 |
| 计算和付款 | 发布结算明确标为 `calculation_snapshot`；实际转账另记 | 计算快照不会自动抵扣实际应付 |
| 运行安全 | 容器生产启动拒绝默认或短 JWT 密钥；复用并释放数据库 HTTP 连接 | 升级前须确认已有私密 `JWT_SECRET`，避免启动失败；不要随意更换现有密钥 |
| 错误诊断 | 响应含 `X-Request-ID`，记录路由模板、耗时、状态；格式错误不回显原输入 | 日志系统需配置采集级别及告警；本轮未配置云端告警 |

## 历史确认 API

三个接口均要求旅行创建者；前缀为 `/v1/trips/{trip_id}`。

1. `POST /history/prepare`：仅对有消费、无已启动结清操作的旅行进入待确认。迁移会为符合条件的旧旅行自动打待确认标记，不自动修改实际结清结果。
2. `POST /history/preview`：请求 `mode=unpaid|settled|partial`；返回 token、拟补转账记录和剩余账单。预览不写入。
3. `POST /history/confirm`：提交同一选择及 token；账单或选择变化返回 409，需重新预览。

`partial` 的 `payments` 每项包含 `date`（消费归属日）、`currency`、`amount`、`from_participant_id`、`to_participant_id`，可选 `paid_on`（实际转账日期）。示例：某日应付 200，补记该日已付 170，则剩余 30。方向须与该日当前负债一致，不能超过剩余额；跨日历史转账需明确拆分日期。无法确认日期或金额的历史账单应暂留待确认，不制造已付款数据。`paid_on` 不明时保留空值，不用导入时间冒充实际转账时间。

待确认期间不能普通结清，首页不把这些历史金额计入可结清总额，并提示“历史结算待确认”。修改过的旧数据会使确认预览失效。原消费后来删除时，确认依据仍在历史快照中。

分页接口：`GET /v1/trips/{trip_id}/expenses/page?limit=50&after_id=...`。返回 `items`、`next_after_id`，按 ID 升序；limit 为 1–100。客户端需持续翻页到游标为空，再做全量计算；不要只用第一页计算结算。

## 数据库升级顺序

生产上线前先核查实际表、函数、历史数据及服务版本。生产应暂停账务写入，取得可恢复的升级前数据库备份，并在独立环境试恢复；不能只凭“导出成功”就认定可恢复。

- CloudBase 网关路径：确认旧基础 schema、协作权限等历史增量已存在，再执行 `20261021_daily_settlement.sql`、`20261022_backend_hardening.sql`、`20261022_business_backup.sql`。已有版本不要重复盲跑；先核对远端迁移历史。
- 正式通过 MCP 应用 DDL 前，将本轮 SQL 按内容不变的方式登记到 `cloudbase/migrations/<14位UTC时间>_<名称>.sql`，预览计划后以同一版本应用，并复查远端迁移记录。`infra/cloudbase` 仍保留仓库历史 SQL 原件。
- SQLAlchemy 直连路径：在已备份、已确认连接目标后运行 Alembic `upgrade head`。新增修订 `20261022_07` 会补齐历史缺失的协作表和创建者成员关系，并回填支付投影及历史待确认标记。不要对同一数据库混用两套迁移记账。
- 先数据库、后后端容器，随后验证旧列表、保存、协作权限、按日/当前旅行结清与撤销。新后端依赖新增批量 RPC，不能只更新代码而不更新数据库。
- 索引创建和历史回填会有锁及执行时间；实际耗时、数据量和多实例并发尚需生产同类环境验证。

Alembic 降级只移除本轮投影和新增索引，保留可能既有的协作表及 JSON 审计历史。CloudBase 不提供自动销毁型回退脚本。上线异常时先停止写入，保留数据库审计记录及新版本依赖，必要时在独立恢复环境验账；不可直接覆盖生产库。

## 业务备份与恢复工具

本轮 `tsb_export_business_backup` 仅适用于 **完成本轮迁移后的 CloudBase PostgreSQL**，由服务端角色读取 14 张业务表，包含结构列清单和校验和。它不是升级前备份工具，也不包含数据库角色/授权、DDL、存储中的小票图片、对象桶策略或服务配置；升级前需另用平台数据库备份能力，并确认图片和配置的恢复方案。

环境变量通过安全的运行环境注入 `CLOUDBASE_ENV_ID`、`CLOUDBASE_APIKEY`（或 `CLOUDBASE_API_KEY`），不把凭证写进命令或日志。脚本校验显式环境 ID，并拒绝覆盖已有输出。可在仓库根目录运行：

```powershell
python scripts/business-backup.py export --env-id travel-split-bill-d2de9oe339ea50 --output backups/business.backup.gz
python scripts/business-backup.py prepare-restore --archive backups/business.backup.gz --output backups/restore.sql
```

先创建本地 `backups` 目录。备份包含私密账务及 token 哈希，目录已加入忽略；应加密保存并限制访问。脚本只生成恢复 SQL，不连接目标库执行。恢复目标必须是独立空环境、结构版本匹配且已安装相同触发器；任何非空表、结构差异或恢复数量不符会中止事务。工具限制解压后 50MB，超过时改用数据库原生备份。恢复后重新导出比对所有业务表，再验算账单、成员、转账和撤销；同步验证关联小票可访问性。

## 验证边界

本地后端接口测试、前端契约测试和官方 WXML/WXSS 编译已执行。`scripts/verify-backend-hardening-pg.mjs` 在可销毁 PGlite PostgreSQL 中检查迁移、历史待确认、竞争 CAS、投影原子性、历史金额不可修改、批量查询、全表备份恢复相等、非空目标拒绝与角色权限。PGlite 的请求排队不能替代真实多连接、多实例数据库并发及负载验证。

生产验证仍需：确认升级前备份和恢复点、迁移预览、实际多客户端并发、云托管私密配置、上线错误日志和监控告警。线上状态以实际检查记录为准。
