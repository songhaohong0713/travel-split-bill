
# Offline old-trip merge

This tool uses only Python's standard library and never connects to a database. `apply` means writing a **new local review package**, not importing into CloudBase or changing the source. `prepare-sql` additionally creates an executable, guarded SQL transaction for a current-schema export; it never executes it. Production merge has not been performed.

```powershell
python scripts/trip-merge.py preview --source C:/private/preupgrade.json.gz --output C:/private/merge-plan.json
# Open the plan locally, review every group and blocked entry; copy its digest.
python scripts/trip-merge.py apply --source C:/private/preupgrade.json.gz --plan C:/private/merge-plan.json --confirm DIGEST_FROM_PREVIEW --output C:/private/merged-review.json
python scripts/trip-merge.py prepare-sql --source C:/private/current-backup.json.gz --plan C:/private/current-plan.json --confirm DIGEST_FROM_CURRENT_PREVIEW --output C:/private/merge.sql
python -m unittest discover -s scripts/tests -p test_trip_merge.py
```

Use your installed Python executable if `python` is unavailable. Output files must not exist. Keep source, plan and output in private storage: the plan contains trip/member IDs and place names, and the review package contains the complete private export. Console output contains only counts/digest or generic errors; it never prints records. The decompressed input limit is 50 MB. No dependencies, credentials, SQL execution or automatic network requests are involved in the Python tool. SQL files contain private source data in hex and must also remain private.

Accepted sources: JSON containing `tables`, `travel-split-preupgrade-v1` (plain or gzip), or the checksummed `travel-split-backup-v1` envelope (plain or gzip). Backup checksum is verified; preupgrade archives do not provide an internal checksum, so the preview binds the entire decoded source with SHA256. The source and plan are recomputed on apply; source edits, plan edits or a changed confirmation digest are rejected. The script does not evaluate SQL/schema/function strings from the archive.

Grouping requires identical place names after stripping a leading 8-digit or 4-digit date prefix (`20261001札幌`, `1002札幌`, `1003札幌` become `札幌`), the same two **actual member IDs**, the same default currency and the same owner. Requiring the same owner avoids silently transferring administrative rights. Dates come only from expense `occurred_at`, never the name or creation time. Every source trip must have nonempty, valid, gap-free actual expense dates, and the combined range must overlap or be adjacent. Gaps split groups. Missing dates/members and conflicting ledger state are blocked. Currency within expense payloads is preserved exactly; different default currencies never merge. No currency conversion or expense/split rewriting occurs.

The lexically smallest source trip ID is the deterministic target. All top-level `trip_id` columns in all exported tables are redirected using `aliases`; expense, payment, receipt, version, invite, share and other row IDs remain unchanged. Receipt object keys remain unchanged (the tool does not copy or delete storage objects). Payment allocations retain payment IDs. Duplicate membership rows are collapsed only in the proposed tables to respect `(trip_id,user_id)` uniqueness; every original membership row and joined date remain in `original`. Historical calculation versions and their public results remain intact; the target's latest-version pointer is cleared to avoid presenting a source-only calculation as the merged result. Existing links/invites are retained, so the operator must review their wider merged-trip access before any future import.

Ledger payment entries retain IDs, timestamps, revocation, allocations and audit fields; differing entries for the same payment ID block the group. Closed date lists are united. Additional ledger maps are combined only when shared keys agree; conflicting values block the group. Original ledger revisions, frozen bases and historical confirmations are preserved in `original`. The proposed target ledger uses revision zero and `history_confirmation.status=pending`; this is intentionally an offline draft requiring fresh reconciliation. Calculation snapshots and `latest_version_id` **never** establish actual payment. Only `payment_records` and ledger `state_json.payments` are actual-payment evidence, including revoked records. The tool preserves both independently and does not invent missing payments or silently promote calculation snapshots to paid status. Where the two sources disagree, an operator must reconcile them before import.

The output format is `trip-merge-review-package-v1`, with `import_ready:false`. It includes the exact decoded original export, confirmed plan, source-to-target aliases and proposed tables. It is **not** a business-backup archive and must not be passed to `business-backup.py prepare-restore` or the preupgrade restore script. Original schema metadata remains under `original`; the proposed tables may use fields introduced after the preupgrade schema. Embedded historical payloads, idempotency response bodies and SQL metadata deliberately remain exact historical evidence and may contain old trip IDs; aliases are the resolution map, not a promise that an old online URL works.

A future import requires a separate reviewed migration: restore the original archive into a new isolated database with its original constraints, run the matching incremental migrations, apply aliases transactionally with owner/access review, reconcile ledger/payment projections and frozen date bases, regenerate revisions and confirmation tokens, validate every foreign key/unique constraint and receipt reference, compare all expense/split amounts and payment/revocation/audit counts against the original, and rehearse rollback. Rebuild payment projections only after confirming their equivalence to immutable ledger entries; existing restore helpers regenerate projections and cannot by themselves prove independently exported payment records were preserved. Test both members' read/write access and share/invite behavior in that isolated target. Only a separately authorized production procedure with a fresh export and maintenance window may follow. The optional confirmed SQL route below implements this transaction for the supported current schema. Preupgrade sources must first be restored and upgraded in isolation, then exported anew for SQL preparation.


## Confirmed executable SQL for the current schema

`prepare-sql` requires a fresh complete 14-table current-schema export and a preview generated from exactly that export. It rejects empty plans, missing/extra tables, candidate trips with **any invite/share-link rows** (including expired or revoked rows), payment records missing from ledger state, differing payment payloads and differing allocation records. Such blocked SQL preparation leaves the read-only preview and original source available; it never deletes records to make the merge proceed. Owner differences are already excluded by grouping. Review-only packages remain useful for old archives.

The generated SQL starts a transaction, takes a fixed transaction advisory lock, locks all 14 source tables in exclusive mode and compares every live row of every table with the exported snapshot. That exact comparison covers ledger revisions, users, login tokens and unrelated trips too: even a routine login after export can require a fresh export/preview/confirmation. This is intentionally conservative and requires a maintenance window. A 10-second lock timeout prevents waiting indefinitely.

Before mutation it inserts the exact original source and confirmed plan into `public.trip_merge_archives`, keyed by confirmation digest. The archive has RLS enabled and all privileges revoked from PUBLIC, anon and authenticated. It is intended for database-owner audit/rollback preparation, not app access. No trigger is disabled. Expenses, receipt images, calculation snapshots and payment records are remapped; receipt jobs and allocations retain their original parent IDs. Target memberships retain their original IDs/dates; redundant source memberships remain in the archive. The merged ledger advances above the highest source revision and runs the existing immutable-payment projection trigger. Payment projections and allocations must remain exactly equal after remapping. Source trip rows and source ledger rows are removed only after archiving and redirecting references. The target remains history-pending, has refreshed date range and no stale latest-calculation pointer.

Before commit, exact final table comparisons verify every row against the planned result, with the expected new ledger revision, followed by immediate constraint validation. Any stale source, trigger incompatibility, unexpected column/table shape, mismatch, orphan or replay aborts the transaction; no partial merge commits. The archive is a full evidence backup, not an automatic rollback script. Restoring it requires a separately reviewed recovery procedure.

Rehearse the generated file against a fresh disposable restore first. After reviewing the result and backing up again, a database owner may execute the generated SQL with a stop-on-error client, for example `psql --set ON_ERROR_STOP=1 --file C:/private/merge.sql` against the explicitly selected target. Do not paste its contents into public logs. The tool does not select a target, log in, execute SQL or modify production. The historical aliases are stored inside the archive plan; old online trip URLs do not automatically redirect. Embedded audit snapshots/idempotency response bodies retain historical IDs unchanged.
