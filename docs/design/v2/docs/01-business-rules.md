# 01 · 业务规则

这些规则在画面上看不出来，但最容易实现错。请把金额相关逻辑集中在一个模块（建议 `utils/money.js`），并按第 7 节的例子写单元测试。

## 1. 角色与范围

- 一段「旅行」= 一个账本。当前版本只支持**两人**：「我」和一位同行人。
- 同行人在界面上显示**微信昵称**（稿里用「小周」「阿杰」举例），头像用昵称的最后一个字（「周」）。
- 所有文案都是**以当前查看者为视角**写的：同一笔欠款，收款方看到「小周待付你 / 待收款」，付款方看到「你待付小周 / 待付款」（付款方视角的页面还没设计，见 06）。

## 2. 币种显示（最重要）

| 情况 | 写法 | 例子 |
|---|---|---|
| 结算币种（旅行设置里选的，默认人民币） | 符号 + 金额，2 位小数 | `¥235.97` |
| 外币 | 金额 + 空格 + ISO 代码，**不带任何符号** | `1,280 JPY` |
| 外币折算成结算币种 | 前缀 `≈ ` | `≈ ¥54.22` |

- **「¥」只代表人民币。** 日元绝对不能写成 `¥1,280`，因为人民币和日元都用 ¥，混在一起会算错钱。
- 千分位逗号：`19,561 JPY`、`¥1,204.50`。
- 小数位按币种最小单位：JPY 0 位，CNY 2 位（用 ISO 4217 的 minor unit）。
- 表格表头写单位：「实际支付（元）」「应承担（元）」。
- 金额数字用等宽数字（tabular-nums），右对齐的列才能对齐。

## 3. 汇率换算

- 每笔消费记录自己的汇率 `rate`（1 外币 = rate 结算币种），默认取**消费当天的中间价**，用户可以在 05b 修改。改了只影响这一笔。
- 换算以**单笔消费**为单位：`cny = roundHalfUp(foreignAmount × rate, 2)`。
- **当天合计、旅行合计 = 各笔换算结果相加**，不要把外币总额再乘一次汇率（两者会差 1 分）。
  例：10月7日 3 笔 = 54.22 + 125.56 + 242.60 = ¥422.38。
- 「实际扣款」（可选，05b）：用户填了信用卡实际扣的人民币金额后，这一笔的换算结果直接用实际扣款，再按各人份额比例分摊（手续费也就按比例分担了），汇率字段显示为由实际扣款倒推的有效汇率。
- 汇率要用十进制计算（例如整数「分」或 decimal 库），**不要用浮点数直接乘**。

## 4. 分摊

三种方式（05 和 05b 的分段控件，见 06 第 1 条的待定项）：

1. **平分**：外币金额按人数平分，按外币最小单位取整，余数归付款人。
   例：1,281 JPY 平分 → 小周 640，我（付款人）641。
2. **按商品**（05b）：每个商品有一个归属标签——`平分 / 我的 / 小周的`。
   - 我的 → 全额算我；小周的 → 全额算小周；平分 → 按规则 1 平分。
   - 个人份额 = 各商品归属金额之和。所有商品金额之和必须等于小票总额，不相等时在「合计」处提示差额。
3. **自定义**：直接输入每人的外币金额，两人之和必须等于总额。

**外币份额 → 结算币种份额：**
- 非付款人的份额：`roundHalfUp(份额外币 × rate, 2)`
- 付款人的份额 = 这一笔的结算币种总额 − 其他人份额之和（让四舍五入的误差由付款人吸收，保证合计永远对得上）

例（05b）：总额 2,964 JPY → ¥125.56；小周 1,106 JPY → ¥46.85；我 = 125.56 − 46.85 = **¥78.71**。

**谁欠谁：** 付款人先垫付了全额，所以非付款人应还给付款人的金额 = 他自己的份额。05 / 05b 的结论句就是这个：「你付了全部 1,280 JPY，小周应还你 ¥27.11」。

## 5. 按天结算

- 每天单独结算。对每个成员：`净额 = 当天实际支付 − 当天应承担`。净额为负的人付给净额为正的人。
- 04 的「分摊明细」表就是这三列：成员 / 实际支付（元）/ 应承担（元）。

**每天的状态（查看者视角）：**

| 状态 | 条件 | 标签样式 |
|---|---|---|
| 今天 · 记录中 | 日期是今天（按旅行所在地时区），当天还会继续记账 | 灰：bg `bg/page`，字 `text/secondary` |
| 待收款 | 当天已过、我是收款方、净额 ≠ 0、未确认收款 | 琥珀：bg `status/pending-bg`，字 `status/pending` |
| 待付款 | 当天已过、我是付款方、未付款（**未设计**，样式同待收款） | 琥珀 |
| 已结清 | 收款方已确认，或当天净额为 0 | 绿：bg `brand/green-subtle`，字 `brand/green` |

- 「记录中」的那天**不计入**待结清合计，也不能合并结清（03 绿卡上的「不含今天」）。
- **确认流程**：付款方可以标记「我已付款」（会通知收款方）；收款方点「确认已收款」后变为已结清。收款方也可以不等对方标记直接确认。
- **撤销**（04b）：已结清后，任一方都可以撤销，需二次确认；撤销后回到待收款 / 待付款。
- **合并结清**（03）：一次结清所有已过、未结清的天，金额 = 这些天的净额之和（¥235.97 + ¥84.03 = ¥320.00），生成一笔转账；确认后这些天全部变成已结清。
- 已结清的那天再补记消费：待定（见 06）。

## 6. 首页汇总与旅行状态

- 「待收款」= 所有旅行中别人欠我的、已过天数的金额之和；「你待付」= 我欠别人的。两个方向都要显示。
- 「来自「东京」· 小周待付你」：只有一段旅行有待收款时显示来源；多段时改成「来自 N 段旅行」。
- 旅行卡片（Trip Card v2）的状态：
  - **待收款**：右侧显示金额（绿色）+「小周待付你」
  - **待邀请**：旅行里只有我一人，右侧「去邀请」（琥珀色）+「只有你一人」，点击直接进入邀请流程
  - **已结清**：右侧「已结清」（灰色）+ 结清日期
  - 「进行中」标签：今天在出行日期范围内时显示；没填日期则不显示
- 排序（01b）：出行日期（最近的在前，默认）/ 最近记账 / 待结清优先；筛选：隐藏已结清的旅行。选中立即生效，偏好存在本地（`wx.setStorageSync`）。

## 7. 单元测试用例（汇率 0.04236）

```
convert(1280 JPY)  = 54.22
convert(640 JPY)   = 27.11
convert(2964 JPY)  = 125.56
convert(5727 JPY)  = 242.60
dayTotal([1280, 2964, 5727]) = 422.38        // 逐笔换算再相加
splitEqual(1280, payer=我) → 我 640 / 小周 640 JPY → 我 27.11 / 小周 27.11
splitEqual(1281, payer=我) → 我 641 / 小周 640 JPY
splitByItems(2964, payer=我,
  [化妆水 1280 我的, 面膜 836 平分, 润唇膏 528 小周的, 卸妆巾 220 平分, 购物袋 100 平分])
  → 我 1858 / 小周 1106 JPY → 小周 46.85 / 我 78.71（合计 125.56）
tripTotal([3180, 1280, 2964, 5727, 4260, 2150]) = 828.60
mergeSettle([235.97, 84.03]) = 320.00
```

## 8. 其他规则

- **邀请**：用小程序分享卡片（`button open-type="share"` + `onShareAppMessage`）把带邀请令牌的链接发到微信聊天，对方点开即加入。
- **「微信提醒小周」**（04a）：同样是分享卡片，内容为当天账单。小程序不能代发起个人转账，所以不要做「去付款」。
- **「复制账单」**（04a）：`wx.setClipboardData`，文本示例：`东京 · 10月7日：小周付给我 ¥235.97（3 笔，共 9,971 JPY，汇率 0.04236）`。
- **登录异常**（06）：已缓存的数据照常显示；新建的旅行先存在本地，用客户端生成的 UUID 作为主键，恢复后上传并按 UUID 去重合并，所以「不会重复」。
- **问候语**：「早上好 / 中午好 / 下午好 / 晚上好」按本地时间切换。
