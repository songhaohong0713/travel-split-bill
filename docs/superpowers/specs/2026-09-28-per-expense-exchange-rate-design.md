# 按消费结算币种与汇率设计

## 目标

让旅行账本中的每一笔消费独立选择结算币种。外币小票可自动换算；最终结算按币种分别生成转账建议，避免把不同币种直接相加。

## 范围

仅支持现有的两位同行人。汇率作用于整笔消费，不作用于单个商品条目。现有小票识别、商品分配、优惠/退款和结算发布继续保持原有行为。

## 消费数据规则

每笔消费保存以下不可变结算依据：

- 小票原币种：来自手工录入或识别结果。
- 本笔结算币种：新建时默认为旅行默认币种，可在消费页修改。
- 汇率：原币种到本笔结算币种的乘数。
- 汇率来源：`same-currency`、`actual-payment`、`frankfurter` 或 `manual`。
- 查询日期与生效日期：自动查询时记录，供用户核对。
- 实际支付金额：可选；填写后其币种自动成为本笔结算币种并锁定该选择，实际支付金额优先作为结算依据。

商品、税费和优惠/退款必须与该笔消费的原币种一致。每笔消费只有一条换算规则，避免同一张小票内部混合汇率。

## 自动汇率流程

当原币种与本笔结算币种不同、且没有实际支付金额时，系统按消费日期请求已有的历史汇率提供方。查询成功后，立即在消费页展示“原金额约等于结算金额”、汇率、取值日期和来源，并将查询结果随该笔消费保存。

当原币种与结算币种相同时，不查询外部服务，汇率固定为 `1`，来源为 `same-currency`。

实际支付金额存在时，不再请求自动汇率：实际支付金额与原币种小计的比例就是该笔消费的结算依据，来源为 `actual-payment`。

## 消费页交互

在“商品条目”下方的“本次消费小计”之后，直接放置“本笔结算”区块，再放置现有“账单调整”。

区块包含：

1. 结算币种选择器；实际支付金额存在时显示为锁定状态。
2. 原金额到结算金额的换算摘要。
3. 自动汇率的生效日期和来源，或“按实际支付金额结算”的说明。
4. “实际支付金额（可选）”输入；币种可选，填入后锁定本笔结算币种。
5. 查询失败时的明确状态、重新查询按钮和手动填写汇率入口。

不对每个商品显示汇率控件，也不把实际支付金额藏入“账单调整”。

## 查询失败与手动补救

查询失败时，消费仍可保存，且已录入商品不丢失。页面显示“未获取汇率，请重新查询或手动填写”。

用户可以重试查询或填写正数手动汇率；手动保存后记录来源 `manual`。存在跨币种消费但缺少汇率时，禁止生成结算预览，并明确指出缺少汇率的消费名称。原币种与结算币种相同的消费不受此限制。

## 结算页

结算预览和发布结果按结算币种分组。每个币种组独立汇总责任、已付款和净额，并独立生成最少转账次数。

例如，一次旅行可同时产生“CNY 结算”和“JPY 结算”两个区块；区块内部只显示该币种金额。不同币种之间不做净额抵消。

## 服务接口与持久化

消费负载扩展为携带结算币种、保存的汇率元数据和可选实际支付金额。后端提供按消费日期、原币种和目标币种查询汇率的受鉴权接口；前端不直接调用外部汇率服务。

结算服务接受同一旅行内不同结算币种的消费，先按币种分组，再复用现有单币种结算算法。已经发布的结算版本保存每个币种组的结果与采用的汇率数据，保证历史结果稳定。

## 验收与测试

- 日元小票结算为人民币时，按消费日期查询并保存历史汇率。
- 实际支付人民币金额会锁定该笔消费为人民币结算，并优先于自动汇率。
- 同币种消费不发起汇率查询。
- 查询失败可保存、可重试、可手动补汇率；缺汇率的跨币种消费不能预览结算。
- 人民币与日元消费可在同一次旅行中结算，结果分为两个币种区块。
- 同一币种区块继续保持两人最少转账逻辑，且发布后结果不会随新汇率变化。
