# 多模态小票识别与翻译设计

## 目标

让用户拍摄或选择日文、英文小票后，获得包含原文、中文翻译、金额和币种的待核对商品候选。模型输出永不直接写入账单。

## 方案

云托管后端复用现有 `receipt_jobs` 队列。后台处理器读取私有小票图片，调用 CloudBase 多模态模型，并要求返回严格 JSON。处理器解析并校验结果后，保存到既有候选字段；小程序现有核对页让用户确认或修改后，再带回商品编辑页。

## 处理流程

1. 小程序上传 JPEG 小票并创建识别任务。
2. 后台处理器领取 `queued` 任务，读取图片。
3. 多模态模型提取日文或英文商品行，翻译为中文，并返回金额、币种、税额和合计。
4. 后端只接受符合结构、金额合法的候选；异常或无效响应进入重试。
5. 小程序展示“待核对”候选；用户确认后手动带入商品条目。

## 模型约束

- 仅处理日文、英文小票；其他语言保留原文并提示手动核对。
- 模型必须只输出 JSON，不提供解释、建议或 Markdown。
- 每项字段为 `source_text`、`translated_text`、`amount`、`currency`；税额和合计仅作候选提示。
- 金额、币种、商品名称缺失或格式非法的项目丢弃，不自动补猜。
- 图片和 API Key 只在后端使用；不对小程序返回图片地址、提示词或凭证。

## 失败策略

- 模型网络错误、非 JSON 响应或无有效条目时，任务最多重试 3 次。
- 最终失败状态为 `failed`，前端显示“识别失败，可手动录入”。
- 用户可继续正常创建、编辑和结算消费。

## 配置与部署

- CloudBase AI+ 中开通支持图片理解的多模态模型与额度。
- 云托管使用专用 CloudBase API Key，通过 `CLOUDBASE_APIKEY` 注入；密钥不得写进仓库或小程序。
- 不创建数据库表或 SQL 迁移；复用现有任务和候选 JSON 字段。
- 部署后先用不含个人敏感信息的日文和英文样例小票验证。

## 验收

- 日文、英文小票分别产生可编辑的中文候选条目。
- 无效模型输出不会进入账单或使任务永久卡在处理中。
- 失败任务在三次后终止并保留手动录入路径。
- 小程序只收到核对所需候选数据，不收到模型凭证或内部调用信息。
