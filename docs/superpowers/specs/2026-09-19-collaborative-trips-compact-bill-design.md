# 协作旅行与紧凑账单设计

## 目标

让一段旅行由两名微信用户共同维护：创建者通过一次性邀请链接邀请同行人加入；两人可读取、新增、修改和删除该旅行内的账单与结算内容。同时将账单录入改成更紧凑的连续列表。

## 已确认范围

- 每段旅行最多两名成员：创建者和一名同行人。
- 两位成员拥有完全相同的编辑权限，且服务端必须校验成员关系。
- 邀请为一次性链接：令牌仅存 SHA-256 哈希，创建后 7 天失效，接受后立即失效。
- 非成员无法读取或修改旅行、消费、结算或邀请；返回 404，避免泄露旅行存在性。
- 原有结算公开分享继续只读，不能获取协作权限。
- 本期不做第三人、成员移除、角色区分、二维码或小程序码。

## 数据与授权

新增 `trip_members`（`trip_id`、`user_id`、`joined_at`，`trip_id + user_id` 唯一）和 `trip_invites`（`trip_id`、`creator_id`、`token_hash`、`expires_at`、`used_at`、`revoked_at`）。创建旅行时拥有者同时成为首位成员。

以 `is_trip_member(trip_id, user_id)` 取代现有仅 `owner_id` 的读写限制。成员才能查询旅行、管理消费、预览或发布结算。成员数为 1 时，任意成员可创建邀请；接受邀请时由数据库事务验证令牌、有效期和两人上限，然后插入同行人并标记 `used_at`。

CloudBase PostgreSQL 用版本化迁移及 RPC 实现同一原子语义：`tsb_create_trip` 同时写入拥有者成员，另增创建和接受邀请 RPC。小程序和任何客户端都不接触 CloudBase API Key、微信 AppSecret 或数据库凭据。

## API

- `GET /v1/trips`：返回当前用户属于成员的旅行，附 `member_count`。
- `GET /v1/trips/{trip_id}/members`：成员可读，返回成员摘要。
- `POST /v1/trips/{trip_id}/invites`：成员创建邀请，返回 `{ token, expires_at }`；成员已满时返回 `409`。
- `GET /v1/trip-invites/{token}`：返回可加入邀请的最小旅行摘要。
- `POST /v1/trip-invites/{token}/accept`：同行人接受邀请并返回旅行摘要。

邀请页为 `pages/trip-invite/index?token=<token>`。创建者可复制或微信转发该路径；令牌不写入日志、Toast 或本地持久化状态。

## 紧凑账单界面

1. 顶部仅显示旅行名、两位成员标签和“成员”入口。
2. 小票是单行入口；未上传时不占用预览区域。
3. 商品采用低高度连续行：第一行是选择、名称、金额、删除；第二行是分账方式；仅选“自定义比例”时出现第三行。
4. 批量分账只在已选商品时显示；税费与优惠默认收起，展示摘要后按需展开。
5. 结算汇总放在普通文档流，绝不使用遮挡按钮的固定定位。
6. 保持现有墨绿、暖白、橙色强调与“旅行票据簿”风格，但降低垂直留白和重复卡片。

## 验收标准

1. 同行人 7 天内可用邀请链接加入；同一链接无法第二次使用。
2. 加入后两人都能看到旅行，且都能创建、更新、删除消费；第三账户无权访问。
3. 至少三项商品可在默认视图连续录入；自定义比例和批量工具只在需要时展开。
4. 添加商品、选择、删除、分账 picker 和结算按钮均可点击，结算区不遮挡内容。
